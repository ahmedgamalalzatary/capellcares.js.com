W06: hold reservations, retries and dispatch against queued payment evidence

Three real defects, all the same root cause: with W04's inbox a verified callback is
durably received before its effects are applied, and three paths acted as though nothing
was pending.

- Expiry released reserved stock for a payment already in flight. The customer had paid,
  the units went back on sale, and the eventual success had nothing to fulfil.
- Public canRetry was true whenever the latest attempt failed, so a sibling attempt with a
  queued success callback invited a second payment. That can double-charge a customer
  whose first payment is merely slow.
- Dispatch created deliveries for orders whose refund callback was still unprocessed,
  delivering goods to someone whose money was being returned, who could then spend the
  refund again.

- Add financial-evidence.repository.ts as the single definition of "unresolved financial
  evidence" (P03/P04). Expiry, retry and dispatch all consult it, and canRetry is derived
  from the same check the mutation paths enforce, so the customer is never offered an
  action the system would refuse.
- Correlate through the SIGNED order.id only, two-sided against an attempt the session
  actually holds. A forged or unknown reference matches nothing. This guard answers
  whether something is pending, never what it claims; interpreting a claim still requires
  an authenticated inquiry.
- Bound expiry: discover candidates with an unlocked read, then recheck each under its own
  lock. No lock is held across the batch. Stale candidates are skipped, never acted on.
- Keep the evidence check lock-free so dispatch can consult it while holding an order lock
  without completing the session/order cycle the plan warns about.

Findings worth recording:

- Surveying every `.for("update")` showed shipping locks order -> shipment -> work item
  and never reads payment_attempts or checkout_sessions, while payment locks session ->
  attempt -> reservations. There was no cycle to fix; the cycle would only have been
  created by the dispatch barrier itself. Problem 2 therefore documents the constraint and
  adds the concurrency test that guards it, which is what made problem 4 safe to land.
- My first concurrency test passed in 69ms and proved nothing. Rewritten so the payment
  path genuinely holds the session lock while expiry runs; it now takes 130ms.
- The evidence correlation was first written as SQL JSON functions and failed twice:
  MySQL 8.4 has neither JSON_UNNEST nor MariaDB's IS NOT NULL(expr). It now correlates in
  application code over the bounded inbox backlog.
- reconciliation_required is treated as terminal: it is a staff decision, not work a
  queued callback resolves, and holding stock on it would strand inventory.
